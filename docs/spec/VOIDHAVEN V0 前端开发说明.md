> **项目名称**：求索袋底洞 | VOIDHAVEN  
> **Slogan**：A haven for seekers.  
> **文档类型**：Frontend Development Specification  
> **版本**：V0 / v0.1  
> **状态**：可作为后续前端 Agent、Codex、工程实现 Agent 的执行基线  
> **目标**：把当前已确认的产品意图、页面结构、关键用户路径、工程约束和验收条件转换为可执行规格。  
> **注意**：本文不是最终产品 PRD，也不是最终视觉设计稿；没有明确冻结的内容，Agent 不得擅自扩展为正式需求。

## 0. 规格状态约定

本文使用三种状态：

- **[冻结]**：已经明确确认，后续 Agent 不得自行修改产品含义或删除。
- **[默认]**：当前推荐方案。Agent 可以做工程级调整，但不得改变业务目标；若调整，应记录理由。
- **[待定]**：尚未完成决策。Agent 不得自行脑补为正式需求，应记录为 `OPEN_QUESTION`。

当工程便利、所谓“最佳实践”与产品规格发生冲突时，优先级如下：

1. `[冻结]` 产品决策；
2. V0 核心用户路径；
3. 前后端接口契约；
4. 可用性与响应式体验；
5. 工程实现便利；
6. 技术炫技、未来假想扩展。

# 1. 项目背景与 V0 边界

## 1.1 项目背景

VOIDHAVEN 来源于一个真实校园场景：

- 校园内竞赛、科研、学习成长信息分散；
- 学生获取信息高度依赖微信群、班群、老师、社团、公众号和熟人关系；
- 一部分有行动意愿的学生不知道有哪些竞赛、什么时候报名、去哪里找队伍；
- 一部分老师、竞赛负责人或学生团队存在招不到合适成员的问题；
- 已有信息渠道偏“通知”或“结果展示”，缺少围绕“赛前发现—组队—行动”的持续信息链；
- 长期愿景不是单纯做一个竞赛公告站，而是逐步形成开放、可传承、有人运营的校园学术成长生态。

但 **V0 不承担全部长期愿景**。

---

## 1.2 V0 核心定位 [冻结]

VOIDHAVEN V0 定义为：

> **面向本校学生的竞赛发现与组队连接平台。通过结构化竞赛信息，以及「团队找成员 / 学生找队伍」双向组队机制，降低学生发现竞赛机会和建立参赛连接的成本。**

V0 的核心不是“建设校园社区”，而是先验证：

> 学生是否愿意通过一个集中、结构化、低门槛的平台完成「发现比赛 → 了解比赛 → 找到团队 / 队友 → 建立后续联系」这一行为链。

---

## 1.3 V0 核心用户价值 [冻结]

### 对普通学生

进入网站后应能快速完成：

1. 看见近期值得关注的竞赛；
2. 判断比赛是否值得继续了解；
3. 查看比赛的完整信息与官方来源；
4. 看见该比赛是否有人正在组队；
5. 选择“团队找成员”或“学生找队伍”的信息；
6. 通过 VOIDHAVEN 的中转机制进一步建立联系。

### 对老师 / 竞赛负责人 / 学生团队负责人

V0 不提供完整账户后台，但应提供：

1. 清晰的投稿说明；
2. 竞赛信息提交规范；
3. 团队招募提交规范；
4. 管理员审核与代发布路径；
5. 不公开私人联系方式的联系中转机制。

---

## 1.4 V0 明确不做 [冻结]

以下功能全部不进入 V0：

- 普通学生注册 / 登录；
- 个人主页；
- 完整 Contributor Dashboard；
- 评论；
- 点赞；
- 收藏；
- 私信；
- 即时聊天；
- 独立论坛；
- 完整博客系统；
- 完整资源中心；
- 完整 Talent Pool / 人才库；
- 简历库；
- 用户能力画像；
- AI Assistant；
- AI 推荐；
- 热门排行算法；
- 复杂权限体系；
- 复杂实名认证；
- Redis / MQ / 微服务等与前端 V0 无关的“企业级”包装功能。

---

## 1.5 V0 品牌表达原则 [冻结]

前端采用：

> **弱品牌表达，强信息吸引。**

首页可以体现 VOIDHAVEN 的气质和品牌识别，但用户进入后必须尽快看到真实、可行动的信息。

### 首页可以有

- `A haven for seekers.`
- “找比赛 · 找队友 · 找机会”
- 极短的一句产品说明；
- Logo / 品牌名称。

### 首页不应有

- 大段项目故事；
- 大幅创始人叙事；
- 长篇使命宣言；
- 首屏纯艺术展示；
- 用户滚动一整屏后才能看到比赛信息。

完整品牌故事放入 `/about`。

# 3. User Flow

## 3.1 Flow A：发现并了解竞赛 [冻结]

```text
首页
  ↓
看到“近期竞赛”
  ↓
竞赛卡片
  ↓
竞赛详情
  ↓
阅读报名时间 / 参赛条件 / 官方来源
  ↓
打开官方信息或继续查看关联组队
```

### 关键用户任务

> “最近有什么比赛值得我关注？”

### 设计要求

- 首页竞赛卡不是完整介绍；
- 它只负责让用户判断“是否值得点进去”；
- 时间信息必须醒目；
- 用户不应依赖站内文本作为唯一权威来源，详情页应保留官方来源链接。

---

## 3.2 Flow B：直接寻找团队 / 队友 [冻结]

```text
首页
  ↓
看到“正在组队”
  ↓
组队列表
  ↓
选择：
  ├── 团队找成员
  └── 学生找队伍
  ↓
组队详情
  ↓
了解需求
  ↓
进入 VOIDHAVEN 联系中转流程
```

### 关键用户任务

> “我已经想参加比赛了，现在需要找到一起参加的人。”

---

## 3.3 Flow C：从竞赛自然进入组队 [冻结，V0 最关键路径之一]

```text
首页 / 竞赛列表
  ↓
竞赛详情
  ↓
“当前有 X 条组队信息”
  ↓
团队找成员 / 学生找队伍
  ↓
组队详情
  ↓
联系中转
```

### 设计目的

竞赛和组队不是两个割裂栏目。

用户不应该：

```text
看完比赛
→ 返回首页
→ 打开组队
→ 重新搜索同一个比赛
```

而应该在竞赛详情页直接看到该比赛的相关组队信息。

---

## 3.4 Flow D：提交信息 [冻结]

```text
任意页面
  ↓
投稿
  ↓
选择提交类型
  ├── 提交竞赛信息
  ├── 团队找成员
  └── 学生找队伍
  ↓
查看规范
  ↓
通过 V0 指定渠道提交
  ↓
管理员人工审核
  ↓
管理员代发布
```

V0 不要求前端实现完整投稿后台或投稿账户体系。

---

## 3.5 Flow E：了解 / 加入项目 [默认]

```text
Footer / Header
  ↓
加入我们
  ↓
了解需要的角色
  ↓
GitHub / 联系入口
```

或：

```text
Footer / Header
  ↓
关于
  ↓
了解项目背景 / 品牌 / 开源理念
```

这两个页面不能抢占首页主体信息空间。

# 4. 全局 Page Shell 规格

## 4.1 Header [冻结]

### 功能

- 展示品牌识别；
- 提供全局导航；
- Logo / 品牌点击返回首页；
- 当前页面导航项应有可识别的 active 状态。

### 响应式

Desktop：
- 品牌左侧；
- 完整导航右侧。

Mobile：
- 品牌保留；
- 主导航折叠为菜单；
- 不允许导航横向溢出。

---

## 4.2 Footer [冻结]

Footer 在主要页面统一存在。

建议至少包含：

### 品牌

- 求索袋底洞 · VOIDHAVEN
- A haven for seekers.

### 探索

- 竞赛；
- 组队；
- 投稿。

### 项目

- 关于；
- 加入我们；
- GitHub。

### 连接

- VOIDHAVEN 社群 / 联系入口。

### 版权

- `© 2026 VOIDHAVEN`

---

## 4.3 响应式原则 [冻结]

必须支持：

- Desktop；
- Tablet；
- Mobile。

产品功能和内容结构不因设备发生语义变化，只改变布局。

示例：

```text
Desktop:
近期竞赛 | 正在组队

Mobile:
近期竞赛
↓
正在组队
```

具体 breakpoint 属于前端工程实现细节。

---

## 4.4 数据状态 [冻结工程要求]

所有数据型页面至少必须处理：

- Loading；
- Success；
- Empty；
- Error。

不接受“只有正常有数据时页面才成立”的实现。

# 5. Page Spec：Home `/`

## 5.1 页面目标 [冻结]

首页在 3–5 秒内让用户明白：

> 这里可以找比赛、找队友、找机会。

并立即暴露真实内容。

---

## 5.2 内容结构 [冻结]

推荐顺序：

1. Header；
2. Compact Hero；
3. 近期竞赛 + 正在组队；
4. 投稿 CTA；
5. Footer。

---

## 5.3 Compact Hero [冻结方向]

建议文案结构：

```text
A haven for seekers.

找比赛 · 找队友 · 找机会

汇集本校正在发生的竞赛与组队机会。

[浏览竞赛] [寻找队伍]
```

### Hero 约束

- 不占满整个首屏；
- 在常见桌面设备中，首屏最好已经能看到下方真实信息区域的标题或首张卡片；
- 不出现完整项目故事。

---

## 5.4 Desktop 主体布局 [冻结]

```text
近期竞赛             正在组队
Upcoming             Find Your Team
Competitions
```

采用左右双栏。

两栏业务权重同级。

### 设计意图

视觉上强化：

> 比赛 ↔ 人

之间的联系。

---

## 5.5 Mobile 主体布局 [冻结]

改为上下：

1. 近期竞赛；
2. 查看全部竞赛；
3. 正在组队；
4. 查看全部组队。

---

## 5.6 首页竞赛卡 [冻结核心信息]

最突出：

1. 报名截止时间；
2. 当前组队状态 / 数量。

### 推荐字段 [默认]

- 比赛名称；
- 类型；
- 适用对象（仅在信息可靠时展示）；
- 截止时间；
- 组队状态。

### 示例

```text
全国大学生数学建模竞赛
数学建模 · 本科生

09 / 10 截止

● 2 条组队信息
```

### 点击

整张卡或明确 CTA 进入 `/competitions/:id`。

---

## 5.7 首页组队卡 [冻结]

必须从卡片层面区分：

- `团队找成员`
- `学生找队伍`

### 团队找成员推荐字段

- 类型标签；
- 团队 / 发起方名称；
- 关联竞赛；
- 核心需求；
- 缺口人数（如提供）；
- 截止时间（如提供）。

### 学生找队伍推荐字段

- 类型标签；
- 年级 / 学院等非敏感基本信息；
- 目标竞赛；
- 能力摘要；
- 状态。

### 禁止

- 首页卡片直接展示私人微信号、手机号等联系方式。

---

## 5.8 首页操作 [冻结]

必须可完成：

- 点击 Logo → 首页；
- 浏览竞赛 → `/competitions`；
- 寻找队伍 → `/teams`；
- 竞赛卡 → 竞赛详情；
- 组队卡 → 组队详情；
- 查看全部竞赛 → `/competitions`；
- 查看全部组队 → `/teams`；
- 投稿 → `/submit`；
- Footer 导航正常。

# 6. Page Spec：Competition List `/competitions`

## 6.1 页面目标 [冻结]

提供完整竞赛浏览入口。

首页负责“发现”，列表页负责：

> “我想系统地看目前有哪些比赛。”

---

## 6.2 页面内容 [默认]

- 页面标题；
- 简短说明；
- 状态筛选；
- 可选类型筛选；
- 当前结果数量；
- 竞赛列表；
- Empty / Error State。

---

## 6.3 V0 状态筛选 [默认]

建议：

- 全部；
- 报名中；
- 即将开始；
- 已结束。

---

## 6.4 类型筛选 [默认，允许根据 Mock 数据规模简化]

例如：

- 算法 / 程序设计；
- 数学建模；
- 创新创业；
- 设计 / 工程；
- 其他。

如果 V0 数据太少，可以暂时减少筛选项，但组件结构应允许未来扩展。

---

## 6.5 排序 [冻结方向]

默认采用时间驱动，而不是“热度驱动”。

优先考虑：

- 报名中；
- 截止时间较近。

V0 不构建“热门竞赛”算法。

---

## 6.6 列表项必须能快速回答

- 这是什么比赛？
- 现在还能不能参加？
- 什么时候截止？
- 有没有组队信息？

---

# 7. Page Spec：Competition Detail `/competitions/:id`

## 7.1 页面目标 [冻结]

用户在这里完成对一个竞赛的完整判断，并自然进入下一步行动。

---

## 7.2 推荐信息结构 [默认]

### Hero / Summary

- 比赛名称；
- 状态；
- 类型；
- 级别（如信息可靠）；
- 关键日期。

### 时间信息

- 报名开始；
- 报名截止；
- 比赛日期。

### 适用对象

- 年级；
- 专业；
- 地域 / 学校限制；
- 其他重要参赛资格。

### 官方信息

- 官方网站；
- 官方报名入口；
- 官方通知 / 文件来源。

### 简介

- 比赛是什么；
- 大致做什么；
- 适合怎样的学生。

### 参赛条件 / 规则摘要

仅作阅读辅助。

官方规则优先级高于站内摘要。

### 当前组队 [冻结]

直接展示：

```text
团队找成员
学生找队伍
```

并显示与当前 Competition 关联的组队信息。

### 元信息

- 信息来源；
- 最后更新时间。

---

## 7.3 关键交互 [冻结]

- 官方链接可访问；
- 点击关联组队进入 `/teams/:id`；
- 可返回竞赛列表；
- 无组队信息时明确显示 Empty State，并可提供“提交组队信息”入口。

---

# 8. Page Spec：Team List `/teams`

## 8.1 页面目标 [冻结]

让用户既可以：

- 找正在招人的团队；
- 也可以看哪些学生正在寻找队伍。

---

## 8.2 一级分类 [冻结]

必须至少有：

- 全部；
- 团队找成员；
- 学生找队伍。

---

## 8.3 可选筛选 [默认]

- 按关联竞赛；
- 按状态；
- 按截止时间。

V0 不需要复杂人才搜索。

---

## 8.4 Team Card [冻结]

### Team Seeking Members

展示：

- `[团队找成员]`；
- 发起团队 / 老师 / 负责人；
- 关联竞赛；
- 核心需求；
- 还缺多少人（如有）；
- 截止时间。

### Student Seeking Team

展示：

- `[学生找队伍]`；
- 非敏感基本背景；
- 目标竞赛；
- 技能 / 能力摘要；
- 希望加入怎样的团队。

---

## 8.5 隐私约束 [冻结]

列表页绝不直接展示：

- 微信；
- 手机号；
- 私人邮箱；
- QQ号；
- 其他可直接用于骚扰的私人联系方式。

---

# 9. Page Spec：Team Detail `/teams/:id`

## 9.1 页面目标 [冻结]

帮助用户判断：

> “我适不适合和这个团队 / 学生建立联系？”

---

## 9.2 公共字段 [默认]

- 类型；
- 关联竞赛；
- 状态；
- 发布时间 / 截止时间。

---

## 9.3 团队找成员详情 [默认]

可包含：

- 团队 / 发起方介绍；
- 已有成员情况；
- 需要人数；
- 需要的能力；
- 不要求什么（用于降低新人理解门槛，若投稿者提供）；
- 预计投入时间；
- 当前准备阶段；
- 其他要求。

---

## 9.4 学生找队伍详情 [默认]

可包含：

# 14. 前端工程约束

## 14.1 前后端分离 [冻结]

前端不得依赖后端内部实现。

通信边界必须是：

> **API Contract**

推荐逻辑：

```text
UI
↓
Page / Feature
↓
Service
↓
API / Mock
```

禁止：

```text
UI Component
↓
直接散落 axios / fetch
```

---

## 14.2 Mock First [冻结]

第一阶段前端必须可以在没有真实后端的情况下完整运行。

建议：

```text
mock/
  competitions
  teams

services/
  CompetitionService
  TeamService
```

开发时：

```text
MockCompetitionService
MockTeamService
```

后期切换：

```text
HttpCompetitionService
HttpTeamService
```

页面不应因此被重写。

---

## 14.3 业务数据禁止硬编码在组件内 [冻结]

禁止把具体比赛作为静态 JSX / Vue Template 内容写死。

错误示意：

```html
<h2>全国大学生数学建模竞赛</h2>
```

作为真实业务数据来源。

正确：

```text
CompetitionCard
← CompetitionSummary
```

---

## 14.4 建议前端目录 [默认]

```text
frontend/
└── src/
    ├── pages/
    ├── components/
    ├── features/
    ├── services/
    ├── types/
    ├── mock/
    ├── assets/
    ├── styles/
    └── router/
```

具体框架目录结构可根据技术栈调整。

---

## 14.5 关键前端数据类型 [冻结概念，字段待 API Contract]

至少存在：

- `CompetitionSummary`
- `CompetitionDetail`
- `TeamSummary`
- `TeamDetail`

组队类型至少能表达：

```text
TEAM_SEEKING_MEMBER
STUDENT_SEEKING_TEAM
```

具体命名可以工程化调整，但业务语义不得丢失。

V0 前端 Mock 数据字段、查询与 Service 边界以 `mock-data-contract.md` 为准。未来 HTTP API 应在 Service 层映射到同一前端领域类型；Mock 字段不自动等同于后端 API 字段。

---

## 14.6 UI Component 责任边界 [冻结]

展示组件负责：

- 渲染；
- 局部交互；
- 视觉状态。

展示组件不负责：

- 核心业务规则；
- 权限真相；
- 数据库规则；
- 直接访问数据库；
- 擅自决定信息可见性政策。

---

## 14.7 状态与边界情况 [冻结]

所有列表 / 详情必须考虑：

- Loading；
- Empty；
- Error；
- 不存在 ID / 404；
- 字段缺失；
- 可选信息为空；
- 过期比赛 / 过期招募。

---

## 14.8 可访问性 [默认]

至少要求：

- 语义化 HTML；
- 可键盘访问主要操作；
- Button / Link 用途明确；
- 有文本的错误反馈；
- 不仅依靠颜色表达状态；
- 图片存在替代文本；
- 合理 heading 层级。

---

## 14.9 响应式与内容韧性 [冻结]

页面不能只针对当前 Mock 数据“刚好排得下”。

必须能容忍：

- 长竞赛名称；
- 长标签；
- 信息缺失；
- 5 条数据；
- 50 条数据；
- 不同手机宽度。

# 20. 当前 V0 最终冻结摘要

VOIDHAVEN V0 的前端必须体现以下五件事：

1. **用户进入后先看到有用信息，而不是大段品牌故事。**
2. **竞赛是发现机会的入口。**
3. **竞赛和组队直接联动。**
4. **组队同时支持“团队找成员”和“学生找队伍”。**
5. **平台承担连接与中转，但不在公开页面暴露私人联系方式。**

这五项是当前前端设计、Wireframe、视觉方案和 Mock Frontend 的最高优先级约束。
